# Italian voice commands

Voice commands are opt-in. The wolf-and-microphone mark in the study top bar is a toggle: muted gray means off; a gently animated accent means wake detection is armed; a brighter accent and board outline mean Loopo is listening for a command. The same toggle stops capture and releases the voice session. Enabling voice requests microphone permission only after the user taps the mark. After microphone access, Loopo offers Android's **Display over other apps** setting for the background listening glow. If the user declines overlay access, voice commands still work and the glow remains inside Loopo while it is open.

The first opt-in downloads the Italian Vosk model from `loopo-vosk-it-0.22.zip` attached to the matching published GitHub release. The app shows progress, allows cancellation, verifies the pinned SHA-256 `9ec65e75861d1c6c2e457cccd932705340dcdf233f5b239f00733b4de0bf3267`, safely extracts into app-private no-backup storage, and removes the compressed archive. A later activation uses the installed model without network access. Playback files, microphone audio, and transcripts are not uploaded or persisted. A missing or invalid download reports an error; the user can retry by tapping the voice mark. The release APK includes the Vosk runtime but not the model archive.

## Recognition and command flow

PlaybackService owns one voice controller, its armed state, transient feedback, and cancellation. It runs only while a track is loaded and the user has enabled voice. The service becomes a media playback plus microphone foreground service while voice is active, so wake detection can continue while Loopo is backgrounded or the screen is locked. Closing the voice toggle, unloading the track, removing Loopo from Recents, or stopping the service cancels capture. Ordinary playback does not request microphone permission.

Vosk recognizes both wake phrase and command audio at mono 16 kHz on API 26+. One shared loaded model serves sequential AudioRecord leases. A mutex prevents overlap; each lease closes its recorder before the next begins. The wake grammar detects **Ehi Lupo**. After wake, Loopo pauses playback, captures one Italian utterance, and sends its transcript to the deterministic parser. It validates the whole utterance before dispatch, supports documented absolute and relative rate variants and one ordered rate-then-resume chain, and rejects unknown, ambiguous, negated, or out-of-range requests. Rate-only commands leave playback paused. PlaybackService serializes voice commands through its existing session; StudyViewModel and AndroidPlaybackController remain the owners of study and playback state.

The UI reports download, passive wake listening, active command listening, success, timeout, recognition errors, and the recognized transcript where available. Result feedback stays visible for four seconds. The command-listening outline disappears when capture ends. Voice status and transcripts are in-memory only.

`PlaybackService` also observes its existing voice status flow to draw the listening glow above other apps. A shared Android view renders a static, low-opacity layered edge glow inside Loopo when overlay access is unavailable and in a non-touchable `TYPE_APPLICATION_OVERLAY` window when access is granted. On API 28+, a 9-pixel shadow softens the inner edge; older supported versions keep the layered-stroke fallback. Wake listening uses marker A's `LoopA` color; command capture uses marker B's `LoopB` color. The voice toggle asks for overlay access only during its explicit activation flow. Declining it does not block microphone capture.

The overlay does not turn on or keep on the display and does not set lock-screen bypass flags. A display that is off cannot show the glow. Android's keyguard can cover application overlays while the display is locked; Loopo leaves that behavior to the system. Recheck locked-screen visibility on each target device.

## Architecture choice

We compared a persistent AudioRecord whose recognizer changes mode after the wake phrase with two explicit sequential AudioRecord leases sharing one loaded Vosk model. The sequential design is selected: it keeps the microphone transition visible and bounded, closes one capture before opening the next, and uses the existing microphone mutex. It avoids keeping a recognizer in an implicit mixed mode. The two architecture candidates used the same configured model family, so there was no cross-model judge; the decision follows the simpler lifecycle and existing ownership boundaries.

The current universal release APK is about 44.2 MB because it carries native libraries for all three supported ABIs; Vosk contributes about 29.5 MB across those libraries (roughly 9–10 MB for the ABI a device uses). The Italian model is about 49.7 MB compressed and about 91.3 MB expanded. The model transfer and storage occur only after opt-in, and app data can be cleared to remove the installed model. The first-release workflow currently distributes a signed APK through GitHub Releases, not a Play App Bundle.

## Verification and remaining evidence

See [Testing](testing.md) for automated commands and physical checks. Automated tests cover parser boundaries, complete action ordering, download integrity, safe installation, and reuse of the cached model. The API 26 and 36 emulator jobs verify packaging and app integration; they do not validate acoustic wake accuracy. Before release, verify first-download progress, cancel/retry, offline reuse, permission denial/regrant, wake-to-command capture, and chained commands on API 26 and a current physical Android device. The Redmi trial is a useful baseline, not cross-device evidence.

For repeat exercises, use A at the start and B at the end of the track when the user has not set markers. Exact cycle boundaries and optional ChatGPT interpretation remain separate work. See [Italian wake phrase evaluation](https://github.com/p33nah/loopo/issues/45).
